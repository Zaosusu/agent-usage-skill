# 豆包用量系数设计说明（1% = 50 万 token）

> 换算直接用这个系数：`总量 = timeline 百分比 × 500_000`。
> 本文说明**这个 50 万 是怎么定出来的**，以及它的适用边界。
> 复算入口：[`tools/calibrate_doubao.py`](../tools/calibrate_doubao.py)。

返回主文档：[README.md](../README.md) ｜ 系数实现：[`plugins/doubao.py`](../plugins/doubao.py)

```
TOKENS_PER_PCT = 500_000          # plugins/doubao.py

总量 = timeline 百分比 × 50 万
```

---

## 0. 为什么需要这个系数

豆包是**云端应用**，本地没有权威 token 账本，而它的用量接口**只返回百分比**——
timeline API 每条只给 `quota_source.display_text`（如 `"0.15%"`），配额接口只给
`used_percent`，**没有任何绝对 token 字段**。

所以核心问题只有一个：**1% = 多少 token？**

---

## 1. 思路：让分子分母来自同一批事件

直觉上想用「本地真实 token ÷ 同时段百分比」，但时间窗对齐不可靠：本地 IndexedDB
里确实存着逐次调用的真实 `inputTokens/outputTokens`，但它的时间戳是**批量落盘时刻**，
不是调用时刻。用时间窗去框，窗口从 ±0 放宽到 ±60min，算出来的系数会漂移数十倍
⇒ 分子分母不是同一批事件 ⇒ 此路不通。

可用的钥匙是一个此前被忽略的事实：

> **timeline 的每条记录 = 一条 user 消息**（`display_name` 就是消息原文），
> 而本地 agent 会话的 `trajectory.jsonl` 里也存着同一批 user 消息。

于是可以**按消息对齐**：同一条消息，一边是它引发的全部模型调用消耗（本地重建），
一边是它在 timeline 里记的百分比。**分子分母来自同一批消息，口径天然一致**，
不受「漏了哪类用量」影响——漏掉的部分在两边都不出现。

### 先验证对齐是真的（不然一切白算）

| 方向 | 结果 |
|---|---|
| 正向：timeline 条目 → 本地 agent 消息 | 约 **83%** 命中，覆盖约 **80%** 的 Σpct |
| 反向：本地消息 → timeline | 约 **95%** 命中 |

同样重要的一点：既然 timeline 里绝大多数条目都能对上本地 agent 会话，
那「重建法只覆盖 agent 模式所以严重低估」就不成立——**timeline 记录的绝大部分
本来就是 agent 模式对话**，重建法给出的量级才是对的方向。

---

## 2. 定值：取定义式口径

```
① 命中密度 = Σtok(命中) / Σpct(命中)     ← 只覆盖命中批（约 80% 的 Σpct）
   含 system prompt : 约 60.9 万/1%
   不含             : 约 59.0 万/1%

② 账户系数 = Σtok(全量) / Σpct(全量)     ← 定义式 ⇒ 采用
   含 system prompt : 约 49.3 万/1%
   不含             : 约 47.8 万/1%
```

**为什么用 ② 不用 ①**：② 是定义式，口径与用途（把总百分比换算成总量）完全一致；
① 只覆盖命中的那一批，而**命中的 key 偏长任务**（长任务每 1% 代表的原始 token 是
短对话的 7.7 倍）⇒ ① 的密度天然偏高，是「命中批的密度」，不是「账户的系数」。

⇒ **采用 `TOKENS_PER_PCT = 500_000`（49.3 万取整到 10 万粒度）。**

---

## 3. 交叉验证：256K 上下文窗口给出的上界

这一条**完全独立**于匹配率，只依赖一条铁律：**单次 API 调用消耗不可能超过模型上下文窗口**。

`doubao-seed-2-1-turbo` / `-pro` 的窗口 = **256K**（火山引擎官方文档）。本地统计
agent 模式单次「调用时上下文」的中位 / p90 / max 分别约为
**65K / 189K / 243K** tok。

**max 那次是最紧的约束**：最紧的那次调用距 262,144 窗口余量很小 ——
这个余量就是**所有本地看不见的消耗（tool schema 每次重发、推理 token……）每次能占的全部余量**。

| 系数 | 账户均值（示例量级） | 判决 |
|---|---|---|
| 47.8 万 | 明显低于可见 max | ✅ 窗口内（偏小） |
| **50 万** | 与可见 max 相容 | ✅ **现行（定义式）** |
| 55 万 | 略高于可见 max | ✅ 窗口内（非定义式值 ⇒ 不采用） |
| 58 万 | 接近窗口 | ✅ 临界 |
| ≥59 万 | 该次调用突破窗口 | ❌ 物理不可能 |
| 120 万 | 远超窗口 | ❌ 突破窗口 |
| 230 万 | 约 1.1 倍窗口 | ❌ 突破窗口 |

⇒ **系数上界约 58.9 万/1%**（足以否定 120 万 / 230 万，但不能定出真值；真值取定义式）。
50 万 落在区间内、且等于定义式值 ⇒ 采用。

> ⚠️ 上界依赖「本地统计到的调用数 = 账户全部消耗」；若有未落盘的调用，上界相应放宽。
> ⚠️ 若将来 agent 会用 1M 窗口模型，此上界需放宽。

---

## 4. 排除的错值

历史上出现过若干错值，根因高度一致：**重复计算**——把「一次调用」算成了两次。

| 取值 | 排除依据 |
|---|---|
| 150 万 / 120 万 / 230 万 | 让单次均值达到窗口的 71% / 80% / 153%，物理不可能 |
| 113.6 万（重建法 v2） | 在 tool 消息处多加一次「上下文重放」，模型调用数虚增约 1 倍（= assistant + tool，这个数字印在该算法自己的表头里） |
| 500 万 | 无依据的十倍误改 |

复现（用现行数据重跑 v2 算法，`tool` 行计为一次调用）：

| 算法 | 模型调用数 | 重建总量 | 隐含系数 |
|---|---|---|---|
| v2（tool 行也算调用） | 约 5,900 | 约 4.78 亿 | **约 95.8 万** |
| v3（只有 assistant 行 = 一次调用） | 约 2,856 | 约 2.385 亿 | **约 47.8 万** |
| 膨胀倍数 | 约 2.07x | **约 2.01x** | **约 2.01x** |

**这个方向的错误特别危险**——它看起来"更完整、更保守"，实际是虚高。

> 判断原则：**多算法一致 ≠ 多证据。** 若若干"算法"其实是同一基数的加常数变体、
> 或共享同一个错误前提，那么它们的"收敛"只是算术恒等式。
> 只有当各算法的前提互相独立时，一致才有说服力。

---

## 5. 这个数是什么口径

换算出来的**是原始 token 量**（含重复的累积上下文），不是打折后的量——缓存折扣已经被
50 万 这个系数吸收掉了。

验证：本地重建 Σ(每次调用的完整上下文 + 输出) 与 看板 `Σpct × 50 万`
两者相差约 **1.6%**，且重建口径与 WorkBuddy 完全同口径。

---

## 6. 怎么用（三条边界）

| 场景 | 能不能用 50 万 |
|---|---|
| 账户全时段总量换算 | ✅ **就是为它校准的** |
| 推算某个任务 / 某一天的实际 token | ❌ 会低估长任务 3 倍以上 |
| 与其他 Agent 横向比用量 | ❌ 量纲不同，不可比 |

### 边界一：1% ≠ 固定 token 数（按任务长度浮动约 7.7 倍）

按任务长度分型统计：

| 任务类型 | Σpct 占比 | Σtok 占比 | 每 1% 对应的原始 token |
|---|---|---|---|
| 短对话（<3 次调用） | 约 45% | 约 19% | **约 21 万** |
| 中等（3~10 次） | 约 15% | 约 14% | **约 47 万** |
| **长 agent（≥10 次）** | **约 20%** | **约 66%** | **约 162 万** |

**同一份额度，长任务每 1% 代表的原始 token 是短对话的 7.7 倍。**
长任务吃掉约 66% 的 token，却只占约 20% 的额度。

机制：**agent 长循环里绝大部分 input 是重复的累积上下文，云端按缓存折扣计费**，
于是 1% 在长任务里覆盖多得多的原始 token。这也是「本地 token ↔ pct」的对数相关系数
很低的原因——不是对齐错了，而是 **% 本身就是个打折后的计费刻度，不是 token 计数**。

⇒ **50 万 是账户混合平均，不是物理常数。** 若某天以长 agent 任务为主，
真实量级可能是 `pct × 162 万`，是 `pct × 50 万` 的 3 倍以上。

### 边界二：跨 agent 的 token 数不可横向比较

样本对照：

| | WorkBuddy（半日） | 豆包（全日） |
|---|---|---|
| 来源 | 逐轮累加 jsonl 的 `usage.total_tokens`，**`est=0` 精确** | `Σpct × 50 万`，**`est=1` 靠百分比反算** |
| input 占比 | **约 99%** | 本地无计数 |
| output 占比 | **不足 1%** | 本地无计数 |
| cache_read | 占 input 相当比例 | 不可见（已在云端折进 %） |

**根因：WorkBuddy 记的是「传输量」，豆包记的是「折后计价量」。**

- **WorkBuddy = 传输量。** input 是「每轮把整段对话重新发一遍」的累加，本质是流量。
  极端样本会话 `in : out` 可达 **100 : 1 量级**——整个会话累计重发了上亿 token 的上下文，
  模型只产出百万级。该值随轮次近似**二次增长**（Σ 轮次 × 上下文长度），
  与「实际处理了多少新内容」无关。
- **豆包 = 折后计价量。** `%` 是云端打过缓存折扣的**计费刻度**，重复上下文近乎免费，
  所以同样规模的重发流量只扣很少额度；再 × 50 万换算成 token，数字天然小。

⇒ **两边的数字差异不是使用量差异，是量纲差异。**
本看板的正确读法：**同一 agent 内纵向可比，跨 agent 横向不可比。**

### 边界三：总量可信，按天的 token 仅供参考

先说清两件事，别混：

| 项 | 可信度 |
|---|---|
| 每日的 **pct** | ✅ **精确**（按接口逐条 `occurred_at_ms` 真实归属，Σ每日 pct = 总 pct） |
| 每日的 **tokens**（= pct × 50 万） | ⚠️ **仅供参考**，见下 |

也就是说**拆分本身没问题**，问题在 `pct → token` 的换算系数不随日变化：
1% 对应的 token 数随任务长度浮动 7.7 倍（见边界一），而看板每天都用同一个 50 万
⇒ 长任务日低估、短对话日高估。**不要把它当成「那天真的过了这么多 token」。**

按天**修正 token 换算**的三条路都已验证不可行：

| 方案 | 结果 |
|---|---|
| 用 `trajectory.jsonl` 的 mtime 归属日期 | 跨天会话被整体挪到「最后修改日」，明显虚高 |
| 用消息文本与 timeline 对齐 | key 取 `_norm(text)[:40]` 会碰撞（「继续」「好的」等短消息跨会话合并），算出荒谬值 |
| 直接读消息时间戳 | `trajectory.jsonl` **只有 `role` / `content` 两个字段**，不含任何时间字段 |

## 6.5 本地存档：高水位 + 完整时序

**为什么需要**：timeline 返回的是**账户累计消耗**，理论上只增不减；但豆包用量页有
「只展示最近半年的历史记录」——若该窗口也作用于本接口，旧条目会陆续掉出，
累计值就**随时间回落**，看板数字跟着掉。

**存档位置**：引擎的 `data/usage.db`（与 `sessions` / `daily` / `meta` 同库）：

| 表 | 内容 | 主键 |
|---|---|---|
| `agent_high_water` | 累计量高水位（每 agent 一行） | `agent` |
| `agent_usage_history` | 每 agent **每天**的 `pct` / `tokens` 完整时序 | `(agent, day)` |

**只增不减**（两条保证）：

1. 总量取 `max(历史高水位, 本次接口值, 逐日并集之和)`
2. 按天写入用 `max(旧值, 新值)` —— 接口抖动把某天改小，不会覆盖已存的历史

**容差 0.5%**：接口值低于高水位 0.5% 以内视为抖动，正常放行；超过则触发衰减保护，
并在 `source_file` 里标注原因（如 `衰减保护：接口 112.50% 低于历史最高 150.00%（-25.0%），已保留本地存档`）。

**历史窗口收缩也不丢曲线**：每次扫描都把「本地时序 ∪ 本次接口按天」**逐日取大**后回灌，
所以即便接口只回半年，看板的按天曲线仍保有完整历史。

**迁移**：早期版本把高水位存在独立 `data/doubao_history.json`（孤儿文件），
首次运行会自动迁进 DB 并**删除该文件**，避免双份真相。

**查存档**：

```sql
select * from agent_high_water;
select day, pct, tokens from agent_usage_history where agent='doubao' order by day;
```

> 补充：**按天的百分比拆分本身是精确的** —— Σ每日 pct = 总 pct。
> 所以 `agent_usage_history` 里的 pct 时序可信，失真的只是 `pct → token`
> 的换算系数（见边界一）。

## 7. 已知偏差：推理 token 本地不可见

豆包 planner 用 `doubao-seed-2-1-turbo-260628`，配置里 `deep_thinking_auto: optional`，
**确实会产生推理 token**。但 `trajectory.jsonl` 只记 `user` / `assistant` / `tool`
三种 role，**没有任何 reasoning / usage 结构化字段** ⇒ 推理 token 消耗了但本地看不见，
重建值天然偏低。

但它**不足以改变量级**。推理只加在**输出侧**，而 agent 模式的消耗绝大部分在输入侧：

| 推理量 = 可见输出的 R 倍 | 总消耗增幅 | 修正后系数 |
|---|---|---|
| R = 3 | +0.8% | 50.4 万 |
| R = 10 | +3.6% | 51.8 万 |
| R = 20 | +7.5% | 53.7 万 |

**要让 50 万涨到 230 万，总消耗需 +360%，即推理量须达可见输出的 914 倍——不现实。**

**旁证（WorkBuddy 真实 usage 统计）**：全量调用统计中，推理占**输出**约 53%，
但因输入侧占约 99%，推理**仅占总量的不到 1%**。豆包 agent 模式结构相同。

## 8. 一键复现

```bash
python tools/calibrate_doubao.py                 # 只算不改：打印双向匹配率 + 两个口径 + 推荐值
python tools/calibrate_doubao.py --apply         # 写回 plugins/doubao.py
python tools/calibrate_doubao.py --anchor 1.5e8  # 有绝对配额时一击钉死
python tools/calibrate_doubao.py --root "D:/xx/DoubaoWork/User Data/Default"   # 换机器
```

**若能拿到硬锚点，系数可以一击锁死**：豆包用量页「占 7 天额度」旁的绝对已用/总额，
或订阅计划的单窗口配额。

```bash
python tools/calibrate_doubao.py --anchor <一个7天窗口的token数> --apply
```

- 百分比是**累加**的（首窗 + 重置 4 次 = 500%），不是单窗口封顶。
- 该接口返回的是**账户累计总量**：拉全后条目可回溯十余天且未被截断。
  页面标题「占 7 天额度」只是该列的列名，不代表 API 只返回 7 天数据。

### 改算法前的四条铁律

1. **正确模型**：一次 assistant 消息 = 一次模型调用，消耗 = `累积上下文 + 本条输出`。
2. **不可重复算**：别在 tool 消息处额外加一次「上下文重放」——工具结果已经进了 `ctx`，
   下次调用的 `ctx_before` 本就包含它 ⇒ 同一份 input 算两遍，高估约 2 倍。
3. **user 消息本身也是 input**，必须计入累积上下文。
4. **连续 user 消息必须合并成一个工作单元**：用户会连发短消息（「你看看」→「还是这个啊」），
   模型只回一次，而 timeline 给每条都记了 pct。若把整轮消耗全算给最后一条，
   前面的 key 拿到 pct 却 token = 0 ⇒ **系数被系统性拽低 2~4 倍**。应在单元内均摊。

## 9. cookie 配置（必需）

没有 cookie 就拿不到数据，所以这是**必配项**。

配置文件路径：`~/.doubao-usage/config.json`
```json
{"doubao_cookie": "sessionid=xxx; passport_csrf_token=xxx; ..."}
```

> 即使配了 cookie，API 也只返回**百分比**（如 `0.15%`），绝对 token 仍需 × 50 万 换算。

### 网络抖动 ≠ cookie 过期

SSL 层存在偶发抖动（`UNEXPECTED_EOF_WHILE_READING`），会让 `scan` 报
「豆包用量取不到」。**这不是 cookie 过期** —— 判定：`curl https://www.doubao.com/`
能通 + DNS 正常 ⇒ 网络抖动，稍后重扫即可。

加固：
- `_request_page()` 带**指数退避重试 3 次**（0.8s/1.6s）。整轮要翻 80+ 页、
  耗时约 2 分钟，单页抖动不该让整轮白费；HTTP 4xx 属确定性错误，不重试。
- 报错文案按 `_last_error` 的 `('net',…)` / `('auth',…)` **分流**：
  网络类会明确告知「与 cookie 无关，cookie 仍是好的，无需重新登录」，
  避免白跑一趟重新登录。
